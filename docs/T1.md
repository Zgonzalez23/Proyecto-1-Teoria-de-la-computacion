# T1. Propuesta de Extensión Creativa: Operadores NOT / OR y Múltiples Acciones

## 1. ¿Qué agrega al lenguaje?

Tres construcciones que aumentan la expresividad en el dominio IoT/Smart Home:

| Extensión | Descripción | Ejemplo de uso |
|---|---|---|
| Operador lógico `NOT` | Negación de una comparación como prefijo unitario. Permite reglas del tipo "si NO ocurre algo, entonces actúa". | `WHEN NOT movimiento == TRUE THEN apagar_luces;` |
| Operador lógico `OR` | Combina comparaciones con disyunción, junto a `AND`. | `WHEN temperatura > 28 OR humedad > 80 THEN encender_ventilador;` |
| Múltiples acciones | Una misma regla puede disparar más de una acción separada por coma. | `WHEN temperatura > 28 THEN encender_ventilador, abrir_ventana;` |

## 2. ¿Por qué esta extensión?

- Es muy natural en domótica: encender o apagar varios dispositivos a la vez, o actuar ante la ausencia de un evento (`NOT`).
- Es fácil de integrar en una gramática LL(1): `NOT` es un token único que inicia una comparación, y las listas se expresan con recursión por la derecha, sin recursión izquierda ni ambigüedades.
- Se puede probar con los 25 casos de la suite: 20 en `casos_prueba.json` y 5 en
  `casos_limite.json`.

## 3. Ejemplos de sintaxis válida (con extensión)

1. `WHEN NOT movimiento == TRUE THEN apagar_luces;`
2. `WHEN temperatura > 28 THEN encender_ventilador, abrir_ventana;`
3. `WHEN NOT humedad < 40 THEN activar_humidificador;`
4. `WHEN temperatura > 28 AND NOT movimiento == TRUE THEN encender_ventilador;`
5. `WHEN NOT alarma == TRUE THEN desactivar_sirena, enviar_notificacion;`

## 4. Ejemplos de sintaxis inválida (con extensión)

1. `WHEN NOT THEN encender_luces;` → falta la comparación después de `NOT`.
2. `WHEN temperatura > 28 THEN ;` → falta la acción.
3. `WHEN NOT NOT THEN encender_luces;` → doble `NOT` sin comparación al final.
4. `WHEN temperatura > 28 THEN encender_ventilador,;` → coma final sin segunda acción.
5. `WHEN temperatura > 28 THEN encender_ventilador abrir_ventana;` → falta la coma entre acciones.

> **Nota:** `WHEN NOT NOT temperatura > 28 THEN apagar_luces;` es **válido**, porque `<comparacion> → NOT <comparacion>` es recursiva. Está incluido en `casos_limite.json` como caso válido.

## 5. Impacto en la gramática

Terminales nuevos: `NOT` y `OR`.

Las acciones son un solo identificador (sin espacios ni acentos):

```text
apagar_luces          ✔
apagar luces          ✘
enviar_notificacion   ✔
enviar notificación   ✘
```

### Producciones

```bnf
<condicion>       → <comparacion> <condicion_tail>
<condicion_tail>  → AND <comparacion> <condicion_tail>
                  | OR <comparacion> <condicion_tail>
                  | ε
<comparacion>     → NOT <comparacion> | <factor_cond> <op_rel> <factor_cond>
<acciones>        → <accion> <acciones_tail>
<acciones_tail>   → , <accion> <acciones_tail> | ε
```

### Cambios respecto a la versión inicial

| Cambio | Motivo |
|---|---|
| `NOT` pasa de `<condicion>` a `<comparacion>` | `NOT` niega una comparación, no toda la condición. Evita ambigüedad con `AND`/`OR`. |
| `<condicion2>` pasa a `<condicion_tail>` | Es el nombre usado en FIRST/FOLLOW, tabla LL(1) y parser. |
| Se agrega `OR` | La gramática final soporta `AND` y `OR`. |
| `{ COMA <accion> }` pasa a `<acciones_tail>` | Recursión por la derecha, apta para LL(1). |
| `COMA` pasa a `,` | En la GLC se usa el símbolo; `COMA` es el nombre del token en el lexer. |

### Consideraciones LL(1)

- `NOT` inicia una comparación y no colisiona con identificadores ni números.
- No hay recursión izquierda: `NOT` es prefijo y las colas (`<condicion_tail>`, `<acciones_tail>`) recursan por la derecha.
- Se decide con un solo token de lookahead: en `<condicion_tail>` y `<acciones_tail>`, `ε` se elige con FOLLOW (`THEN` y `;` respectivamente).
